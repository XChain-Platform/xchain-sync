## [Unreleased]

### Added
- `src/HubClient.js`, `src/SyncService.js`, `src/api.js` — `GET /health` now reports how stale the sync service's hub view is. Sync re-discovers the chains it replicates from hub config on a 5-minute timer; if the hub went dark it kept replicating against the last chain set it saw while `/health` still reported `healthy`, with no signal that the hub view had gone stale. `HubClient` now records `lastSuccessfulFetchAt` (epoch ms) on every `getallconfigs()` an endpoint answers — including delta polls that changed nothing — `SyncService.getHubConfigAgeSeconds()` derives the age, and `/health` now returns `hub_config_age_seconds` (`null` until the first success). Purely additive; existing `/health` callers are unaffected.

### Changed
- `package.json` — pinned `mariadb` 3.5.2 to exact versions (dropped the `^` caret ranges) so every install resolves a byte-identical dependency tree across operator nodes, matching the versions already frozen in `package-lock.json`. No source changes.
- `src/schema-version.js`, `src/ClientApplier.js`, `src/SnapshotBuilder.js` — `SCHEMA_VERSION` is now a per-`dbType` object (`{ indexer: 2, decoder: 2 }`) instead of a single shared integer. The indexer and decoder snapshot schemas can now advance independently: bumping the key for one DB only forces that DB's validators to refuse stale snapshots, while validators of the unaffected `dbType` keep running. Previously a single shared integer meant any schema or wire-encoding bump — even one touching only one database — forced every validator of both types to restart in lockstep, and schema drift in one DB could not be isolated from the other. Both keys start at `2` (the current shared value), so no validator restart is required on deploy. `SnapshotBuilder` resolves `SCHEMA_VERSION[db.dbType]` for the `X-Snapshot-Schema-Version` header and the snapshot body; `ClientApplier` resolves `SCHEMA_VERSION[this.db.dbType]` (defaulting to `indexer`) for the mismatch check on both full and incremental apply paths. The on-the-wire `schema_version` field stays a scalar integer (the resolved value for that `dbType`), so the snapshot payload shape is unchanged. `test/unit/ClientApplier.test.js` and `test/security/ClientApplier.security.test.js` assert against `SCHEMA_VERSION.indexer` to match the new shape.
- `src/api.js` — migrated all four `rateLimit()` limiters (full-snapshot, incremental-snapshot, transparency, heartbeat) from the deprecated `max` option to its canonical `limit` replacement (renamed in `express-rate-limit` v8, which this service already runs). `max` remains a backward-compatible alias today, so this is a behavior-preserving rename that forward-protects against a future major release dropping it.
- `src/HubClient.js` — `getallconfigs()` now polls the hub incrementally: it echoes the hub's `watermark` back as `since_updated_at` and merges the returned delta into a cached config map, so each 5-minute discovery cycle transfers near-nothing once chains are known instead of pulling the full config tree twice (once for `getIndexerConfigs`, once for `getDecoderConfigs`). The merge is exact because the hub's config table is upsert-only (rows are never deleted); `_extractDbConfigs` still receives the same full map. The client is long-lived (one per `SyncService`), so the cursor persists across cycles and the second call within a cycle reuses the first call's advance. Falls back to a full fetch on the first call, after a restart, or against an older hub that reports no watermark.
- `package.json` — aligned the `mariadb` driver to the `^3.5.2` range used across the platform. The driver was previously pinned to `~3.4.5` (a patch-only range, one minor line behind the `xchain-dashboard` host); the caret range now tracks 3.x minor releases consistently with every other service, removing the version drift and the mix of `~`/`^` range operators across the platform. No source changes.

### Fixed
- `src/validation.js` — `extractColumnDefinition` now rejects a column definition that carries a bare comma at parenthesis-depth 0, closing a DDL-injection path on the schema-catch-up route (`db.addMissingColumns` → `ALTER TABLE ... ADD COLUMN <def>`). The function previously guarded only against a trailing comma (stripped) and an embedded semicolon, but a malicious or MITM'd sync source could return a `SHOW CREATE TABLE` whose new-column line embedded a second action after a bare comma — e.g. `` `evil` int DEFAULT 0, DROP COLUMN balance `` — which MariaDB parses as a single valid multi-action `ALTER TABLE`. With no semicolon and a clean column name, it slipped past `validateDdl`, `validateIdentifier`, and the `multipleStatements:false` connection flag alike, letting the server DROP/RENAME/ADD arbitrary columns on a replica during ordinary schema replication. The definition is now scanned character by character tracking parenthesis depth, and any comma at depth 0 returns `null` (the column is logged and skipped, not spliced); commas inside `(...)` — `decimal(18,8)`, `enum('a','b')`, `varchar(255)` — are part of the type and still parse. `test/security/validation.test.js` adds rejection cases for the DROP/ADD/RENAME comma-injection variants plus a positive `decimal(18,8)` case, and `test/security/ClientSync.security.test.js` adds an integration test asserting the catch-up path skips the injected column instead of issuing the multi-action `ALTER`.
- `src/ClientRollback.js` — `_rollbackIndexer` now purges `price_snapshots` on reorg with its own `DELETE FROM price_snapshots WHERE reference_block >= ?`, mirroring the source indexer. `price_snapshots` anchors each consensus round to a block via `reference_block` (its equivalent of `block_index`) rather than `block_index`/`action_index`, so it falls outside both generic delete loops and was never rolled back on the replica. Live convergence on this table is hub-driven (the hub DB sync mirror delivers `row:deleted` events), but that propagation lags the local reorg — between the indexer rollback and the hub catching up, the replica kept serving `status='finalized'` rows for rounds whose anchoring blocks were orphaned, so any historical price query against the replica referencing an orphaned round returned a stale finalized price. The bespoke delete closes that staleness window; a later hub-driven delete of an already-removed row is a harmless zero-row SQL no-op. Read-path data quality only — sync replicas drive no fee validation, so consensus was never affected. `test/unit/rollback-coverage.test.js` reclassifies `price_snapshots` from `ROLLBACK_EXEMPT` to `SPECIAL_CASE` so the rollback-coverage guard now actively verifies the table is purged on reorg rather than exempting it.
- `src/ClientSync.js` — the decoder live-sync path now detects a fork at the committed tip. The decoder branch of `_handleBlock` checked only for *missing* blocks (a height gap) and let the already-applied skip drop any block at or below the current tip silently, so a block re-delivered at the tip height with a different `block_hash` — a short reorg the client never observed on the live stream — was discarded without action, leaving the replica pinned to an orphaned block. The skip now first compares the incoming `block_hash` against the stored head hash (`this.lastHashes.block_hash`, written on every applied decoder block) and, on a mismatch at the tip height, logs a continuity error and triggers an incremental catch-up — symmetric with the indexer path, which already catches the same class of fault through its chain-hash continuity check. Decoder block events carry only the block's own `block_hash` (the replicated previous-hash reference is a node-local interned ID, not a portable hash), so a head re-delivery is the one fork the stored value can detect without hash-chain math; same-hash re-deliveries (normal multi-source duplicates) and the pre-first-block boot state (`lastHashes` null) fall through to the plain skip unchanged. `test/unit/ClientSync.test.js` gains a `decoder fork guard` group asserting catch-up fires on a differing-hash tip re-delivery, stays quiet on a matching one, and never false-triggers before a hash is stored.
- `src/replicatedTables.js` — `sync_meta` (the transparency log) is now included in the `/status` row-count completeness check. It is replicated to followers (streamed inline by `ServerPoller._buildBlockPayload` and carried by snapshots) but was absent from `getReplicatedTables()`, so a follower that genuinely dropped transparency rows the source streamed went undetected by the completeness signal that already covers every other replicated table. Added a new `special` topology category that `getReplicatedTables()` unions into the check, holding `sync_meta` for indexer (empty for decoder, which has no transparency log). It is deliberately NOT placed in `blockScoped`: `ServerPoller` reads only `blockScoped`/`txScoped`/`actionScoped`/`index` to build per-block payloads, so listing `sync_meta` there would make `_buildBlockPayload` read the current block's row via `getBlockScopedRows` before `TransparencyLog.recordBlock` has written it (recordBlock runs after payload build in `_poll`) — the record-after-build ordering trap. The `special` category decouples "counted for completeness" from "extracted per block", closing the gap without that trap. The check compares the source's `sync_meta` rows against the replica's replicated copy of those same rows (not rows derived from `blocks`), so the counts track each other and a flagged shortfall is a real drop, not the benign `sync_meta`-lags-`blocks` divergence. This also activates the previously-dormant `sync_meta` entry in `test/unit/rollback-coverage.test.js`'s `SPECIAL_CASE` list, so the rollback-coverage guard now actively verifies `ClientRollback` purges `sync_meta` on reorg. `test/unit/replicatedTables.test.js` gains assertions that `sync_meta` is in the replicated set yet absent from all four per-scope extraction lists.
- `src/ServerPoller.js`, `src/TransparencyLog.js`, `src/sql/merkle_reorgs.sql` (new) — the source node's transparency log is now reorg-aware. On a server-side reorg `ServerPoller` rewound its in-memory cursor and broadcast a reorg event but never pruned its own `sync_meta` / `merkle_epochs` — sync-service-owned tables that nothing else rolls back (the indexer rolls back its data tables, not these). Because `recordBlock` writes `sync_meta` with `INSERT IGNORE` on a `UNIQUE block_index`, the orphaned blocks' rows survived and the re-added canonical blocks' new hashes were silently dropped, so the node then served stale hashes and `verified:false` Merkle proofs for the reorged range; any `merkle_epoch` already committed over that range stayed permanently wrong. The reorg branch now calls a new `TransparencyLog.pruneFrom(block_index)` before broadcasting, mirroring and completing the client's existing `sync_meta` prune (`ClientRollback`) on the source side. Per the chosen policy (track the canonical chain), `pruneFrom` deletes `sync_meta` and `merkle_epochs` from the reorg point so they re-derive from canonical hashes as the chain re-syncs (`recordBlock` re-inserts; `commitEpoch` recomputes the root when the boundary re-crosses), and records each invalidated committed epoch in a new append-only `merkle_reorgs` audit table (`old_root`, plus `new_root` backfilled by `commitEpoch` on re-commit) so every root change is observable to auditors. `pruneFrom` deliberately uses plain `doQuery` rather than the shared db's transaction machinery — that machinery drives the single `transactionConnection` field the snapshot-read path also uses, and adding the poll loop's first transaction races it under fault (proven by the chaos reorg-under-latency test); instead the steps are ordered to self-heal on the poll loop's retry and each is idempotent (duplicate-guarded marker insert, idempotent range-deletes). Indexer-only — the decoder has no transparency log. `merkle_reorgs` is auto-created by `verifySyncTables` like the other sync-service tables. `test/unit/TransparencyLog.test.js` and `test/unit/ServerPoller.test.js` gain coverage of the prune, the audit-marker capture/backfill, the duplicate-guard retry path, and the decoder no-op; verified end-to-end by the `CE-SYNC-03` reorg-under-injected-latency chaos test.
- `src/HubClient.js` — `_call()` now records per-endpoint failure detail on `connector.lastFailures` (a `url → code` entry per unreachable endpoint) alongside the existing per-URL `console.warn`, so a caller receiving `null` can report which endpoints were tried and why each failed instead of only a generic unreachable signal. The `null` return contract for the all-endpoints-failed case is unchanged.
- `src/ServerPoller.js` — the live per-block indexer payload now carries every interned-lookup `index_*` table, not just `index_transactions` and `index_addresses`. `_buildBlockPayload` extracted those two explicitly but left the other eight (`index_actions`, `index_statuses`, `index_tickers`, `index_fiats`, `index_coins`, `index_memos`, `index_mime_types`, `index_pubkeys`) to ride snapshots only. These are append-only string-interning tables, so the first time a value was interned mid-stream — the first instance of a new action type, ticker, status, coin, etc. — its row did not reach a live-syncing follower until the next snapshot backfilled it, leaving dangling foreign-key references (NULL joins) in the interim. Hardcoding the referencing columns was rejected as the fragile path: the references are not a clean suffix convention (`lists.item_id` → `index_tickers`, `orders.give_tick_id`/`get_coin_id`, etc.), so a new action type or column would silently reintroduce the gap. Instead, the new pass pools every `*_id` value present in the block's already-assembled payload and fetches matching rows from each remaining index table. Over-fetch is harmless: the rows exist on the source and the client applies them `INSERT IGNORE` on the primary key (all ten index tables are already in `ClientApplier.ignoreTables`), so the replica's `index_*` set stays a subset of the source's and never overshoots the `/status` row-count completeness check. Indexer-only (`dbType !== 'decoder'`); `index_transactions`/`index_addresses` keep their existing precise joins (they carry block-hash/tx-hash IDs the generic `*_id` scan can't see). `test/unit/ServerPoller.test.js` gains a regression assertion that a new action/status/ticker/coin interned in a block rides the live payload, plus a guard that the decoder never queries the indexer-only index tables.
- `test/e2e/helpers/decoderFixtures.js` — `truncateAll()` now also clears `mempool_transactions`. The decoder schema defines that table but the test-reset helper's `DELETE` list omitted it, so a stale mempool row could survive between e2e runs and skew assertions that re-seed decoder state against a shared database. Added in child-table-first order alongside the other unparented tables; it has no foreign key, so position is not constraint-sensitive.
- `src/SnapshotBuilder.js`, `src/ServerPoller.js` — the decoder `events` table is now re-dumped in full on every incremental snapshot instead of being skipped. `events` is advertised in the decoder replicated topology (`replicatedTables.js`, decoder `index` bucket) and rides full snapshots, but `streamIncrementalSnapshot` had it in `decoderSkip` while `ServerPoller._buildBlockPayload` also skips it per-block (it has no `block_index`/`tx_index` cursor to scope by). A `ServerPoller` comment claimed "full/incremental snapshots will catch them up" — factually wrong, since incremental snapshots never emitted it. The result: a follower that bootstraps via full snapshot and then transitions to incremental catch-up received zero new `events` rows for the gap period, with no error, metric, or operator signal — a silent, unrecoverable drift whose only fix was a full re-bootstrap (rate-limited to 1/hr/IP). Moved `events` from `decoderSkip` into `decoderFullDump` so every increment carries a complete dump; this is idempotent because `events` has an `AUTO_INCREMENT id` PRIMARY KEY carried in the payload and `ClientApplier.applyIncrementalSnapshot` applies all incremental rows with `INSERT IGNORE` (existing ids no-op, genuinely new ids insert). Corrected the misleading `ServerPoller` comment to describe the actual convergence path. `events` is operational/logging and not consensus-critical, so ledger correctness was never affected — but the completeness guarantee advertised by the topology and the `/status` row-count check is now actually met. `test/unit/SnapshotBuilder.test.js` gains a regression assertion that a decoder incremental snapshot emits the full `events` table.
- `src/replicatedTables.js` — removed `dispensers` from the decoder per-block replicated topology (`TOPOLOGY.decoder.txScoped`). The per-block stream captures only rows *inserted* in a block (via the `tx_index`→`block_index` join), but the decoder prunes expired dispensers every block with a count-reducing `DELETE` (`deleteOpenDispensers`) that the insert-only stream cannot represent. Streaming inserts alone let a follower's `dispensers` count grow monotonically above the source forever and publish a `/status` count no complete replica could ever match — a permanent false row-count divergence for this table in any decoder-side completeness check. `dispensers` now converges via the full snapshot only (`SnapshotBuilder.streamFullSnapshot` dumps current rows in full, reflecting prunes). No reader queries the decoder replica's `dispensers` table, so dropping it from the per-block set is behavior-preserving for consumers. `test/unit/replicatedTables.test.js` gains a regression assertion that `dispensers` is absent from the decoder set.
- `src/replicatedTables.js`, `src/ClientRollback.js`, `src/SnapshotBuilder.js` — the per-block replication topology referenced three attestation tables (`attestation_requests`, `attestation_responses`, `attestation_validator_signatures`) that no longer exist: they were consolidated into a single `attests` table (one row per ATTEST `action_index`, covering v0 request / v1 response / v2 expire) when the attestation framework landed. `ServerPoller` queried the phantom tables every block, MariaDB threw, the bare `catch` swallowed the error, and nothing attestation-related was streamed — while `attests` itself was absent from the topology entirely. Replicas therefore received correct attestation state only at snapshot boundaries (`SnapshotBuilder` discovers tables via `information_schema`, so full/incremental snapshots picked up `attests`); between snapshots all new ATTEST activity was silently dropped, and `ClientRollback` could not roll the orphaned range back on reorg. Removed the three phantom names and added `attests` to the action-scoped set in both the streamed topology and the reorg rollback list; `attests` carries `action_index`, so it rides the existing per-block action_index join with no special-casing. Also dropped the dead `attestation_validator_signatures` entry from `SnapshotBuilder`'s incremental block-scoped set (it never matched, since the table is absent from `information_schema`). `test/unit/rollback-coverage.test.js` gains a targeted regression assertion that `attests` is in `ClientRollback.dataTables` and the phantom split names are not, so the consolidation can't silently un-wire again. **Operator note:** any replica that processed a reorg on an older build still carries orphaned ATTEST rows in `attests` that this stream-time fix does not retroactively purge — force a full snapshot on each affected replica after deploying to overwrite them.
- `src/ClientRollback.js`, `src/SnapshotBuilder.js`, `src/replicatedTables.js` — corrected the running per-validator attestation aggregate table name from `attestation_validator_stats` to its actual MariaDB schema name `attest_validator_stats` in the reorg cleanup `DELETE` (and three accompanying comments). Because the `DELETE` named a table that does not exist, `ClientRollback`'s orphaned-row purge threw on every reorg, was swallowed by the surrounding `catch`, and silently no-op'd — leaving stale, over-counted `fulfilled_count`/`missed_count` rows on the replica until the next full snapshot overwrote them, instead of the intended "rows absent until next snapshot" recovery the comment documents. The replica still cannot recompute these counts (it lacks the capability/governance snapshot needed to derive the responsible set), so dropping the orphaned rows and waiting for the next full-snapshot ride-along remains the correct model — this fix simply makes that drop actually execute. The source indexer (`xchain-indexer/src/rollback.js`) already uses the correct `attest_validator_stats` name and fully recomputes, so it was never affected. **Operator note:** a replica that processed a reorg on an older build still carries stale `attest_validator_stats` rows this stream-time fix does not retroactively purge — force a full snapshot on each affected replica after deploying to overwrite them.
- `src/HubClient.js` — the hub JSON-RPC client now remembers the last endpoint that answered and starts each call there (wrapping through the remaining endpoints), instead of always trying the configured endpoints in fixed order. Previously, when the first endpoint was degraded enough to hit the request timeout, every call paid the full timeout penalty before falling back — and then retried that same endpoint first on the next call. At a 60s refresh interval with a 5s timeout the worst-case overhead was `N × 5s` per interval (N = endpoint count). The client now sticks to a known-good endpoint until it too fails, then rotates to the next responder.
- `src/ClientSync.js` — a decoder full-snapshot bootstrap now cross-checks the source's published per-table row counts before declaring itself complete. Previously the only post-bootstrap verification was `_verifyAgainstSource`, which short-circuits for any non-indexer DB type, so the `VERIFY_HASHES` gate that triggered it was a no-op for decoder: a truncated snapshot (network cut mid-stream, or a source serving stale data) was accepted as complete with no row-count check and no warning, then propagated downstream to any indexer built on the incomplete replica. Bootstrap now routes decoder to a new `_verifyDecoderCompleteness`, which fetches the second source's `/status` row counts and runs the existing `_verifyTableCounts` shortfall check — independent of `VERIFY_HASHES`, since row counts need no synthetic chain-of-state hashes. A shortfall is logged loudly as `TABLE_COUNT_MISMATCH` (additive health signal, matching the indexer path); a transient `/status` fetch failure is swallowed so it does not abort an otherwise-good snapshot. Only active when more than one `SYNC_SOURCES` is configured. `test/unit/ClientSync.test.js` gains coverage of the completeness check and the bootstrap wiring (decoder runs the check regardless of `VERIFY_HASHES`; indexer keeps the hash path; single-source skips it).

### Security
- `src/db.js`, `src/ClientSync.js` — table names supplied by a remote sync source are now validated before they reach a SQL identifier. The replica's `/status` poll carries a `table_counts` map whose keys are table names; the client's `_verifyTableCounts` passed each key straight into `db.getTableCount`, which interpolates it into a backtick-quoted `` SELECT COUNT(*) FROM `<table>` `` (identifiers can't be parameter-bound), so a malicious or MITM'd source could break out of the quoting with a crafted key (e.g. a stray backtick + `UNION`/subquery) and read arbitrary data from the replica's database. `_verifyTableCounts` now runs `validation.validateIdentifier` on every key and skips + logs any that fail (a bad key can't even manufacture a false count mismatch and trip a needless recompute/halt), mirroring the existing schema-application loop. As defense-in-depth `getTableCount`, `getTablePage`, and `truncateTable` in `db.js` also re-assert the identifier at the SQL boundary and throw before querying, protecting every caller regardless of input source. Unit tests cover the malicious-key skip in `_verifyTableCounts` and the boundary rejection in all three `db.js` helpers.
- Pinned `ajv` to `^8.18.0` via `overrides` in `package.json`. The mutation-testing toolchain (`@stryker-mutator/core`) pulled in `ajv@8.17.1` transitively, which `npm audit` flagged for a moderate ReDoS in the `$data` schema option (GHSA-2g4f-4pwh-qvx6, fixed in 8.18.0). The dependency is dev-only and the affected code path is not exercised, but the override forces the patched 8.20.0 line so `npm audit` reports zero vulnerabilities and CI audit gates pass. No production code or `@stryker-mutator/core` declarations changed.

### Added
- `.env.example` — added a configuration template enumerating every environment variable the service reads (server/client mode, hub coordination, replica database, WebSocket and snapshot tuning), with safe defaults and inline comments. Also added `.env` to `.gitignore` so a populated local `.env` is never committed.
- `src/db.js` — the MariaDB connection pool now sets `queryTimeout: parseInt(process.env.DB_QUERY_TIMEOUT) || 30000`. Without a query timeout a slow or lock-blocked statement had no upper bound and could hang a pooled connection indefinitely, stalling replica DB application with no timeout-based recovery. A query now aborts after the configured timeout (30s default, overridable via `DB_QUERY_TIMEOUT`) instead of hanging. Matches the pattern already used by `xchain-hub`.
- `src/api.js` — new `GET /health` endpoint. `/status` reports per-chain block heights and lag but not whether a replica database connection has tripped its circuit breaker open after repeated failures (which halts block application while the process stays up). `/health` lists each replicated database's circuit state and returns HTTP 503 when any is open, so monitoring can tell a healthy replicator apart from one stalled on a database outage.
- `src/BlockBroadcaster.js` — each WebSocket subscriber entry returned by `getSubscribers()` (surfaced through `/status` and `/validator-status`) now carries a `heartbeatReceived` boolean. The per-subscriber `lag` field is `lastSentBlock - appliedBlock`, but `appliedBlock` is only known once the subscriber sends a heartbeat — so `lag` is `null` both for a subscriber that has never reported and (conceptually) for one whose state is simply unknown, conflating "no data yet" with any other null cause. Clients that never send heartbeats — legacy builds, third-party validators — would therefore always appear with `lag: null`, indistinguishable from a caught-up peer. `heartbeatReceived` is `true` once the subscriber has reported an applied block at least once, giving operators and monitoring tooling an unambiguous signal to tell an unknown lag apart from a real measurement (including a genuine `lag: 0` caught-up state). Purely additive — existing `lag`/`appliedBlock` semantics are unchanged.
- `src/BlockBroadcaster.js`, `src/api.js` — `/status` and `/validator-status` now expose an explicit machine-readable lag-known/lag-unknown signal so an operator or alerting script no longer has to infer what a null lag means. (1) Each WebSocket subscriber entry from `getSubscribers()` gains a `lagStatus` field — `'known'` once a heartbeat has established a baseline (so `lag` is a real number, including a genuine `0` = caught up) and `'unknown'` when no heartbeat has arrived (so `lag` is null because it is undetermined, not because the subscriber is in sync). Previously a never-heartbeated validator showed `lag: null` and was visually indistinguishable from a healthy zero-lag peer to any script scanning only for non-zero lag. (2) `getValidatorHeartbeats()` (named-validator REST heartbeats, surfaced through `/validator-status`) now returns a structured `{ validators, total, unknown_count }` object instead of a bare validators map: each validator entry carries a `status` of `'known'` | `'unknown'` (unknown = `lag_blocks` could not be computed because the source height is not yet known), and `unknown_count` aggregates how many recorded validators have a genuinely undetermined lag versus a real `0`. This is a response-shape change for both `/validator-status` routes (the validators map is now nested under a `validators` key alongside the counts), so any external tooling keyed on the previous flat shape must update. Note: this surfaces unknown-lag state only for validators that have POST'd at least once — the service holds no roster of *expected* validators, so a validator that has never sent a single REST heartbeat cannot be enumerated here. `test/unit/BlockBroadcaster.test.js` gains `lagStatus` assertions on the subscriber-lag cases and a new `getValidatorHeartbeats` group covering the empty, unknown, known, caught-up, and mixed-set tallies.

### Changed
- `WS_BACKPRESSURE_LIMIT` (consecutive buffered sends before a slow WebSocket subscriber is force-disconnected) is now env-configurable via `process.env.WS_BACKPRESSURE_LIMIT` (floored at 1), instead of being hardcoded to 50. Lets operators tune disconnect tolerance for validators with heterogeneous replica DB speeds. Default is unchanged at 50.
- The Docker image is now built with `npm ci` instead of `npm install`. The committed `package-lock.json` is copied into the build context and `npm ci` installs the exact dependency tree it records, failing the build if the lockfile is missing or out of sync with `package.json` rather than silently resolving newer transitive dependency versions.

### Fixed
- `src/SyncService.js` / `src/config.js` — `_waitForHub()` now gives up after `MAX_HUB_WAIT_MS` (new env var, default 300000 = 5 min) instead of retrying forever. A fresh deploy against an unreachable hub previously hung silently in an unbounded `while(true)` ping loop with no timeout and no process exit, so a process supervisor saw a running-but-stuck service and never restarted or alerted. On expiry the loop logs a `console.error` naming the hub host/port and exits non-zero. The progress line also now fires every attempt (every 3s) instead of every tenth attempt (every 30s), so operators get prompt feedback. `MAX_HUB_WAIT_MS` is documented in the README `.env` examples; raise it for environments that intentionally bring the hub up after sync.
- Regenerated `package-lock.json` so it matches `package.json`. The lockfile still pinned `axios@^1.6.7` while `package.json` had moved to `^1.16.0`, leaving the two out of sync. (Required for the `npm ci` build above to succeed.)

### Added
- Replica-completeness verification on the client. The sync `/status` endpoint publishes a `table_counts` map for the per-block replicated table set (see `src/replicatedTables.js`), and `ClientSync._verifyAgainstSource` now compares the source’s counts against the follower’s own (via `db.getTableCount`), logging a `TABLE_COUNT_MISMATCH` for any table the source has rows in that the follower is missing. The committed ledger/actions/contract hashes are replicated verbatim from the source, so a follower missing entire tables still agreed on every hash; this adds an independent completeness signal the hash check cannot provide. Additive only — it never overrides a passing hash result. Covered by new `_verifyTableCounts` cases in `test/unit/ClientSync.test.js`.
- `test/unit/rollback-coverage.test.js` — a rollback-coverage guard. It reads the set of tables `ServerPoller` replicates (per dbType) and asserts every one is handled by `ClientRollback` on reorg (rolled back, recomputed, special-cased, or explicitly exempt with a reason), for both the `indexer` and `decoder` DB types. `ClientRollback`'s table lists are a hand-maintained mirror of `xchain-indexer/src/rollback.js` and have drifted before; this fails at CI time when a replicated table is left unhandled, instead of surfacing as silent replica divergence after a reorg.
- `ClientRollback.js` — the decoder rollback table lists are now exposed as `decoderBlockTables` / `decoderTxScopedTables` constructor properties (a single source of truth `_rollbackDecoder` consumes), so the coverage guard can verify the decoder path. Behaviour is unchanged.
- Per-subscriber applied-block tracking so operators can observe validator lag from the server side before the backpressure limit force-disconnects a slow subscriber. `BlockBroadcaster` now records `_syncLastSentBlock` (highest block pushed to each subscriber) and `_syncAppliedBlock` (highest block the subscriber reports having committed), the latter fed by a new inbound `{ type: 'heartbeat', appliedBlock }` message handler — the WebSocket channel was previously server→push-only. `ClientSync` sends that heartbeat after each committed live block, debounced (every 10 blocks or 5s, whichever comes first) to avoid a round-trip per block during fast sync. Regression coverage added in `test/unit/BlockBroadcaster.test.js`.

### Fixed
- `ClientSync.js` — the `/status` gap check in `_handleEvent` now uses a strict `>` (`event.block_height > lastAppliedBlock + 1`) instead of `>=`. A status event reporting the source exactly one block ahead is the normal steady state — that block arrives over the live WebSocket stream — so `>=` fired a redundant out-of-band incremental catch-up on every status tick during live sync, racing the live apply. Only a shortfall of two or more blocks is a real gap; this mirrors the decoder gap check in `_handleBlock`, and a genuinely dropped block is still picked up on the next status tick. Fixes the previously-failing `does not trigger catch-up when no gap` unit test.
- `db.js` / `ClientSync.js` / `SyncService.js` — schema replication now propagates columns added to a table after a replica was first built, instead of only ever creating whole missing tables. Previously both schema paths (`replicateSchema`'s direct source-DB copy and `ClientSync._fetchAndApplySchema`'s server `/schema` fetch) skipped any table that already existed locally, so a column introduced upstream never reached a pre-existing replica — the first snapshot or per-block INSERT carrying that column failed with `Unknown column ... in 'field list'` and rolled back, permanently stalling sync for that table until the column was added by hand. `db.addMissingColumns(table, sourceDdl)` now closes the gap generally for every already-existing table, deriving each missing column's definition from the authoritative `CREATE TABLE` DDL (validated, semicolon-guarded) and applying it with a best-effort `ALTER TABLE ... ADD COLUMN` before any snapshot transaction opens. `db.ensureReplicatedColumns()` is a DDL-free backstop for the `give_ownership`/`get_ownership` columns on `orders` and `swaps` (added for token-ownership trading; both `TINYINT(1) NOT NULL DEFAULT 0`, so the ADD COLUMN backfills existing rows safely) — it runs at the tail of `replicateSchema` and unconditionally in `SyncService`'s client-mode discovery, so an indexer replica self-heals these columns on next startup even when the source DB is unreachable and no DDL is available. Scoped to indexer replicas; tables absent locally are left for fresh creation.
- `ClientApplier.js` / `ClientRollback.js` — the `balances` and `contract_balances` rebuild steps no longer swallow every error. They previously caught and discarded all exceptions to tolerate the expected missing-table case on a decoder replica (`ER_NO_SUCH_TABLE`, errno 1146), but that also hid real DB failures mid-rebuild (lock-wait timeout, connection drop, arithmetic cast overflow), letting the block/rollback transaction commit with stale or empty derived balances and no log entry — a silent divergence from the source. The catch now rethrows anything that isn't errno 1146, so genuine failures propagate to the containing transaction's handler, which rolls back, logs, and rethrows as it already does for every other table.
- `ClientRollback.js` — `_rollbackIndexer` now drops the orphaned-range rows of `attestation_validator_stats` on reorg (those with `last_updated_block >= block_index`), so the replica no longer serves overcounted per-validator `fulfilled`/`missed` aggregates after a chain reorg. Unlike on the source, the replica does NOT recompute these rows: `attestation_validator_stats` is never block-streamed (it only rides along in full snapshots), and the thin replica DB lacks the capability/governance machinery the source uses to reconstruct `missed_count` from the responsible-set snapshot — reproducing that math here would re-introduce the indexer-mirror drift the rollback-coverage guard exists to catch. Correct counts are restored from the (now reorg-safe) source on the next full-snapshot ride-along, the same recovery model already used for `markets`. `rollback-coverage.test.js` reclassifies the table from exempt to special-case.
- `ClientRollback.js` / `ClientApplier.js` — the replica now recomputes the `contract_balances` custody aggregate from the surviving `valid` `deposits`/`withdrawals` rows, mirroring how `balances` is already derived from `credits`/`debits`. `contract_balances` has no `action_index` column, so the source poller's action-scoped JOIN errors for it and it is never streamed per-block — meaning it was previously only ever populated from a full snapshot, leaving stale contract custody balances after a reorg (and stale between snapshots during normal forward sync). `ClientRollback` rebuilds it inside the rollback transaction (after `balances`); `ClientApplier` rebuilds it whenever a block payload or incremental snapshot touches `deposits`/`withdrawals`. The companion derived table `markets` is deliberately left to snapshot recovery: reproducing the source's OHLCV recompute (`getMarketInfo` — last-trade / 24hr price-high-low-change-volume / bid / ask over `orders`/`order_matches`/`dispenses`) in the thin replica DB would re-introduce the very indexer-mirror drift the rollback-coverage guard exists to catch. `rollback-coverage.test.js` reclassifies `contract_balances` from exempt to recomputed and documents the `markets` decision in its exemption note.
- `ClientRollback.js` — added `prices` to the action-scoped `dataTables` rollback list (kept in sync with `xchain-indexer/src/rollback.js`). The table carries an `action_index` and is streamed live via both `ServerPoller.actionScopedTables` and `infraTables`, but was absent from the rollback list, so a reorg left orphaned PRICE rows on the replica — serving prices that were never finalized on-chain through replica-backed read paths until the next snapshot.
- `ServerPoller.js` — removed `delegates` from `actionScopedTables`. No such table exists (the real table is `delegations`, also listed), so the per-block payload query for it errored and was silently swallowed every block.
- `ServerPoller.js` — removed `markets` from `actionScopedTables`. The table has no `action_index` column (it's a derived OHLCV aggregate keyed by tick pair, with an auto-increment `id` PK and a `last_updated` timestamp cursor), so `getActionScopedRows`'s `action_index` JOIN errored and was silently swallowed every block after bootstrap — market stats (bid/ask/last/volume) on a replica stayed frozen until the next full/incremental snapshot. Removing it makes the code match the actual behaviour (snapshot-only refresh) and drops the per-block silent failure; an inline comment records that live per-block accuracy would require rebuilding `markets` on the follower from `order_matches`/`dispenses`. `ClientRollback.dataTables` already omits `markets` (it was never block-rolled-back), so no rollback change is needed; the `rollback-coverage.test.js` exemption note is updated to drop the now-stale "lists it under actionScopedTables" wording.
- `SnapshotBuilder.js` — `streamFullSnapshot` and `streamIncrementalSnapshot` now read the block-height anchor, the hash headers (`X-Ledger-Hash` / `X-Actions-Hash` / `X-Contract-Hash`, or `X-Block-Hash` for decoder), and every paginated table inside a single `REPEATABLE READ` transaction opened with a consistent snapshot before the anchor read. Previously these reads ran with no transaction boundary: the headers were captured first, then the multi-table loop streamed pages one at a time, so a source commit landing mid-loop produced a payload whose rows mixed two block heights while the headers advertised only the first.
